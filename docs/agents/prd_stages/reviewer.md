## Feasibility（可行性验证门禁）

> Writer Phase 1 完成后，在进入 Reviewer 之前执行可行性验证。

检查项：
- PRD 中引用的每个 API 端点是否在调研摘要中有出处？
- PRD 中每个枚举值是否来自 API 文档或用户确认？
- PRD 中是否有未标注来源的数据字段？
- PRD 中是否有编造的内容（零容忍）？

输出：`versions/{v}/agent_comm/{task_id}/03_feasibility_report.md`

---

## Reviewer（PRD 评审员）

```
Step 1. 读取 PRD 初稿

Step 2. 完整性检查（7 维度，满分 100；维度与分值的权威定义见 `docs/verification/quality-gates.md` §2.1）

        [15分] 图先行 + 概述（Chapter 1）
        - 业务完整流程图 Mermaid 是否存在且嵌入 Ch1.1？（缺失扣 3 分）
        - 业务完整流程图是否为简化横向流程（区别于 Ch2.1 技术流程）？
        - 业务完整流程图是否有文字图注（D07）？
        - 非目标是否明确列出？
        - 术语表是否包含英文标识符列？
        - 成功指标是否可衡量？
        - 范围是否包含前置依赖？

        [35分] 流程与规则（Chapter 2）
        - 2.1 核心流程图是否覆盖业务全链路？是否最小颗粒度（D05：节点拆到可独立验证子步骤、关键约束一句话上卡，与 §2.2.x 逐步对齐）？
        - 2.1 核心流程图是否符合 UML 活动图语义（D03：stadium 起止/判断菱形带分支标签/分支显式合并）？
        - 2.2.x 每个子流程是否均有 Mermaid 图（W13，文字仅作图注补充）？
        - 状态流转是否有状态机图且符合 D04（[*] 初终态、转移标注含事件）？（缺失扣 5 分）
        - 业务规则索引是否完整（R01/R02/... 编号）？
        - 边界与异常是否已列出？
        - ⚠️ 规则是否无重复定义？（整篇 PRD 搜索，确认每条规则只在 2.4 出现一次）

        [5分] 使用场景（Chapter 3）
        - 场景是否覆盖典型业务情境（创建/调整/异常/生命周期等）？
        - 场景数是否 3~5 个？每个场景是否只含 4 要素（场景背景≤2句 + 示意图+图注 + 关键规则 + 对应页面）、无「系统行为举例」长段？
        - 场景是否只引用规则编号（R01/R02...），不重复规则内容？
        - 是否有统一示例背景（运营角色 + 店铺 + 站点）？

        [30分] 交互原型（Chapter 4）
        - 每个 4.x 模块是否标注对应原型文件名？
        - 每个 4.x 模块是否包含「标注点说明」表格？说明是否只写交互逻辑（无样式描述）？
        - 标注点编号是否与原型 HTML 中 annotation-point 一致？
        - 交互行为是否引用规则 ID 而非重复？
        - 字段定义是否含「数据字段」列（inline code）？

        [10分] 格式规范（逐项检查）
        - F01-F11 逐项检查（每违反一条扣 1 分，扣完即止）

        [5分] 简洁可读
        - 每章缺「本章要点」块扣 1 分（grep -c "本章要点" 应为 4）
        - 场景数 >5 个，每多 1 个扣 1 分
        - 单段落 >3 行（F11），每处扣 0.5 分（本项上限 2 分）
        - 全文 >700 行（wc -l），扣 2 分
        - 本维度 5 分扣完即止

Step 2b. HTML 呈现检查（已生成 HTML 渲染版时必检）
        - HTML 版流程图/状态图必须用 mermaid.js CDN 直接渲染 MD 权威源（D06），
          若为静态 PNG 截图 → 违反 D06，扣 5 分并退回 HTML 渲染阶段
        - HTML 中图源代码与 MD 逐字一致（同一权威源，禁止双份维护）
        - 图绘制质量按 D08 清单核验（见 docs/rules/prd-diagram-standard.md）

Step 3. 评分判定
        - ≥ 80分：通过，进入最终输出
        - 60-79分：自动返回 Writer 修改，附修改建议
        - < 60分：自动返回 Researcher 补充调研
        - 自动返工上限：最多 2 次（引用规则 W20）；超过后暂停流水线并向用户报告未通过维度与扣分项

Step 4. 输出《PRD 评审报告》
        写入：versions/{v}/agent_comm/{task_id}/05_prd_review_report.md
```

## Reviewer 检验

> 每项标注【机器可验】/【人工判定】（引用规则 W21）。

- [ ] 【机器可验】完整性评分 ≥ 80 分（`grep` 提取 `05_prd_review_report.md` 评分值比对；通过线权威定义见 `docs/verification/quality-gates.md` §2.1）
- [ ] 【机器可验】6 个维度评分明细完整（`grep` 报告中 6 个维度名及各自分值均出现：概述15/流程与规则35/使用场景5/交互原型30/格式规范10/简洁可读5）
- [ ] 【机器可验】格式规范 11 项逐项检查完毕（`grep -o "F0[1-9]\|F1[01]" 05_prd_review_report.md | sort -u | wc -l` = 11）
- [ ] 【人工判定】所有不通过项有明确修改建议（判定要点：每个扣分项附具体修改指向，含章节号或规则编号）
- [ ] 【机器可验】评审报告包含评分明细（`grep -c "分" 05_prd_review_report.md` ≥ 5）

## 最终检验

> 每项标注【机器可验】/【人工判定】（引用规则 W21）。

- [ ] 【机器可验】PRD Markdown 文件已写入版本目录（`test -s versions/{v}/prd/*-prd.md`）
- [ ] 【人工判定】用户已确认 Markdown 内容（判定要点：确认信号判定见 `docs/rules/sop-writing-standard.md` W14）
- [ ] 【机器可验】HTML 渲染版已生成（仅用户确认后；`test -f versions/{v}/prd/*-prd.html`）
- [ ] 【机器可验】评审报告已产出（`test -f versions/{v}/agent_comm/{task_id}/05_prd_review_report.md`）
- [ ] 【机器可验】评分 ≥ 80 分或已按建议修改（`grep` 提取报告评分值比对）
- [ ] 【机器可验】PRD 中标注了关联原型路径（`grep -c "proto-" versions/{v}/prd/*-prd.md` ≥ 1）
- [ ] 【人工判定】**三文件同步完成**：MD、主 HTML、独立原型 HTML 三文件已同步修改且编号一致（判定要点：章节编号、标注点编号、交叉引用逐处比对）
- [ ] 【机器可验】**技术契约已移除**：PRD 不包含技术契约章节（`grep -c "技术契约" versions/{v}/prd/*-prd.md` = 0）
- [ ] 【人工判定】**HTML 增强**：图片灯箱 + 原型内嵌 + 模态容器 + JS 交互完整（判定要点：浏览器打开 HTML 逐项验证四类增强可用）
