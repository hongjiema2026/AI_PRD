# SOP 编写规范

| 属性 | 值 |
|------|-----|
| 版本 | v1.8 |
| 适用范围 | 全项目所有 SOP 文档（见 frontmatter `scope`） |
| 创建日期 | 2026-07-28 |
| 状态 | active |
| 规范模版来源 | `versions/eBayPLP广告策略_v0.1.0`（章节体系 / 规则编号 / 附录变更记录打法） |

> 本规范是**所有 SOP 文档的唯一编写标准**。任何新建或修改 SOP 文档的行为必须先读本文件。
> 规则编号 W01-W32 只在本文件 §3 定义一次，其他文档只写「引用规则 Wxx」。

## §1 目的与核心原则

### §1.1 目的

让 AI 执行 SOP 时**零猜想**：每条规则是可执行判定式（给命令/文件名/阈值/枚举值/边界方向），每个交互卡点的信号词穷举，每项验收标准可判定通过/不通过。

### §1.2 核心原则（迁移自 eBayPLP 模版）

| 原则 | 含义 | 违反后果 |
|------|------|----------|
| 唯一权威来源 | 每类信息只在 1 个文件定义 1 次，其他位置引用编号或章节 | 双份定义 = P0 缺陷，必须消除 |
| 可执行判定式 | 规则含具体命令/路径/阈值/枚举/边界方向 | 模糊表述 = P1 缺陷 |
| 变更可追溯 | 每个文档 frontmatter 带 version，文末附录变更记录表 | 缺失 = 验收不通过 |
| 验收可判定 | 每项验收标准标注【机器可验】或【人工判定】，机器可验项给出检查命令 | 不可判定项 = P1 缺陷 |

### §1.3 不适用范围

- 版本产出物（PRD/原型/操作文档）的编写规范**不由本文件定义**，分别见 `docs/agents/prd_agent.md`（F01-F10/W11-W13）、`docs/agents/proto_agent.md`、`docs/pipelines/doc-pipeline.md`
- 流程图呈现规范见 `docs/rules/flow-diagram-standard.md`

## §2 文档结构模版

### §2.1 文件骨架（固定顺序）

```
---
title: <文档标题>
version: v<主.次>        # 首次创建 v1.0；内容变更次版本 +1；结构重写主版本 +1
date: YYYY-MM-DD         # 本次变更日期
status: active | archived
---

# <文档标题>

| 属性 | 值 |              ← 属性表：版本/适用范围/创建日期/状态/关联文档
...

> 头部 blockquote：一句话定位 + 权威源声明（本文件定义什么、不定义什么）

## §1 目的与适用范围
## §2 <角色与职责 | 术语定义>     ← pipeline 类文档为「流水线概览」
## §3 规则与流程                  ← 主体，规则按 §3 编号体系定义
## §4 检验清单                    ← 每项标注【机器可验】/【人工判定】
## §5 调度接口                    ← 仅 agent 类文档需要；其他类型可省略
## 附录：变更记录
```

- 章节编号：`§1`/`§1.1` 两级为主，`§1.1.1` 三级封顶，禁止四级
- 章节标题 numbered 引用时写 `§3.2`，不写「第三章第二节」
- 文档行数上限：单文档 ≤ 500 行；超出必须拆分子文档（如 `docs/agents/prd_stages/` 模式）。**例外一**：代码级规范（含完整 CSS/JS 模板的文档，如 `html_render.md`）不受此限，但必须在头部 blockquote 声明「代码级规范，允许超行」
- **例外二**：工具入口文件（`AGENTS.md`、`CLAUDE.md`）因工具加载格式约束，免 frontmatter 与属性表，但文末必须有「附录：变更记录」表；行数上限按 `docs/rules/entry-guard.md`（`CLAUDE.md` ≤160 行）

### §2.2 表格样式

- 列数 ≤ 7 列；超出拆行或改用列表
- 列序约定：编号类表格固定首列 `编号`；字段类表格固定 `字段 | 类型/控件 | 默认值 | 说明`
- 单元格内禁止换行；长内容移入表后 blockquote 口径注释

### §2.3 blockquote 口径注释

表格装不下的口径（适用边界、例外声明、同步要求、计算口径）写在表格正下方 `>` 引用块，格式：

> **<口径名称>**：<一句话定义>。<边界方向/例外>。

### §2.4 反引号用法

| 场景 | 写法 | 示例 |
|------|------|------|
| 文件路径/文件名 | 反引号包裹 | `docs/agents/prd_agent.md` |
| 命令/脚本参数 | 反引号包裹 | `python3 scripts/state_manager.py refresh` |
| 英文标识（字段名/枚举键） | 反引号包裹 | `strategy_name`、`wave` |
| 中文枚举值/状态值 | 反引号包裹 | `已结束`、`active` |
| 章节引用 | 不包反引号 | §3.2 |
| 规则引用 | 不包反引号 | 引用规则 W07 |

## §3 规则定义（W01-W32）

### §3.1 唯一权威来源规则

**W01 单点定义**：每类信息（流程步骤、阈值、文件名、信号词、评分维度）只在 1 个文件的 1 个章节定义。其他文档需要该信息时，写引用不写全文。

**W02 引用格式**：`完整定义见 \`文件路径\` §N` 或 `引用规则 Wxx`。禁止「详见某文档」不带章节号的模糊引用。

**W03 SKILL 引用壳**：`.agents/skills/*/SKILL.md` 只含 4 部分——frontmatter（name + description 含触发词）、角色与触发场景（≤10 行）、执行流程摘要（子角色名 + 一句话职责 + 指向权威源的引用）、完成标志/失败信号（引用 `docs/verification/quality-gates.md`）。**禁止在 SKILL.md 内联规则全文**（评分表、格式规范、步骤细则一律引用）。

**W04 权威源归属表**：

| 信息类别 | 唯一权威源 |
|----------|-----------|
| SOP 总流程/卡点/路由 | `AGENTS.md` |
| 各任务流水线细节 | `docs/pipelines/*.md` |
| 各 Agent 执行细则 | `docs/agents/*.md`（含 `prd_stages/`） |
| 评分维度与通过线 | `docs/verification/quality-gates.md` |
| 逐项检验清单 | `docs/verification/checklists.md` 与各 agent 文档 §4 |
| 流程图呈现 | `docs/rules/flow-diagram-standard.md` |
| SOP 文档编写 | 本文件 |
| 入口编辑防护 | `docs/rules/entry-guard.md` |

### §3.2 颗粒度规则（防 AI 猜想）

**W05 可执行判定式**：每条规则必须包含以下适用项：命令（完整可复制）、文件路径（绝对或项目相对）、阈值（数字 + 比较方向）、枚举值（反引号穷举）、边界方向（含「含/不含」端点）。缺适用项且无正当理由的规则视为 P1 缺陷。

**W06 禁止模糊词清单**：以下词出现时**必须**在同句或同段配操作化定义，否则违规：

| 禁止裸用词 | 违规示例 | 合规写法 |
|-----------|----------|----------|
| 等（开放式列举） | 「肯定词或执行指示等」 | 穷举词表 + 「仅以上词命中算数」 |
| 视情况 | 「视情况重试」 | 「评分 <80 重试，最多 2 次」 |
| 简单任务 | 「简单任务至少一行计划」 | 引用 W12 简单任务判定表 |
| 适当/酌情 | 「适当增加说明」 | 「说明 ≤ 3 行」 |
| 尽量 | 「尽量复用组件」 | 「先扫描组件库，命中复用，未命中新建」 |
| 明确（未定义时） | 「用户明确确认」 | 引用 §3.4 信号词判定表 |
| 等（文件/路径省略） | 「修改相关文件」 | 列出全部文件路径 |

**W07 枚举封死**：凡存在有限取值的概念（状态、类型、模式、结果档），必须给出完整枚举表，禁止「包括但不限于」。无法穷举的，写「开放式取值，兜底动作 = <固定动作>」。

**W08 失败文案模板**：面向用户的错误/失败提示，在 SOP 中给出文案模板（含 `{占位符}`），执行者不得自行措辞。

**W09 数字给边界**：所有数量约束写「比较符 + 数字 + 单位 + 端点含否」，如 `>500 行（不含 500）时启用 offset/limit 分段`。

### §3.3 变更追溯规则

**W10 附录变更记录表**：每个 SOP 文档文末固定「附录：变更记录」，表头 `日期 | 版本 | 变更内容 | 同步载体`：

- 日期列格式 `YYYY-MM-DD HH:mm`（24 小时制，精确到分钟），新增行必须带时间；历史行（本规则 v1.3 生效前已存在的行）豁免补时间（依据 W22 零编造，禁止虚构历史时刻）
- 变更内容用「①②③」编号罗列具体改动点，每点写到文件/章节级
- 同步载体列声明本次改动波及的所有文件（如「本文件 + `AGENTS.md` §路由表」）
- 同日期多次变更分行记录，版本号递增
- **新行置顶**：最新变更排在表格首行（按日期时间降序，即最新时间在最上），禁止追加在末尾；日期时间相同按版本号降序；同日期的历史无时间行视为当日 `00:00`，排在同日期有时间行之后

**W11 同步纪律**：修改任何 SOP 文档时，若改动信息在其他文档有引用（按 W04 权威源归属表自查），必须在同一 commit 内同步所有引用点，并在各文件变更记录中互相声明。

### §3.4 交互要求规则（卡点信号词）

**W12 简单任务判定表**（用于卡点①的「至少一行计划」豁免判定）：

| 条件 | 阈值 |
|------|------|
| 涉及文件数 | = 1 |
| 预计改动行数 | ≤ 10 行 |
| 是否影响流程/规则/阈值 | 否 |

三个条件**同时满足**才算简单任务；任一不满足按完整计划流程执行。

**W13 卡点①批准信号判定表**：

| 判定 | 用户回复 |
|------|----------|
| ✅ 算批准 | 「批准」「可以」「执行」「开始」「OK」「确认」「没问题」「按这个来」「就这么办」（含以上词的完整句，如「可以，开始吧」） |
| ❌ 不算批准 | 仅补充需求、纠正理解、提出疑问、只读不回、回复「嗯」「哦」等无指示语气词 |

**W14 文档确认信号判定表**（Writer 等阶段的「用户确认产出物」卡点）：判定表与 W13 完全相同，两处共用不另定义。

**W15 审查通过信号判定表**（卡点②）：

| 判定 | 用户回复 |
|------|----------|
| ✅ 算通过 | 「通过」「审查通过」「没问题」「OK」「可以」「确认」（含以上词的完整句） |
| ❌ 不算通过 | 提出修改意见、指出遗漏、只读不回 |

**W16 意图模糊兜底**：用户输入未命中任何任务路由关键词时，固定动作 = 向用户展示候选意图列表（路由表全量 8 类）供选择，禁止自行猜测路由。

**W17 提问格式**：向用户提问时必须给出可选项（编号列表），禁止纯开放式提问；涉及方案选择时标注推荐项及理由。

**W31 版本关联影响扫描**：卡点①计划生成前（探索环境阶段），凡任务涉及 `versions/{v}/` 产出的修改，必须扫描该版本全部关联产出物并评估是否需同步调整：

- 扫描范围（枚举封死）：`versions/{v}/prd/`（MD + HTML）、`versions/{v}/prototype/`（主 HTML + `pages/` + `components/`）、`operation_docs/` 中同名功能文档
- 输出要求：计划中固定含「关联影响检查」小节，逐对象一行，结论枚举 = `需同步调整`（转为动作明细表的一行动作）/ `无需调整`（附一句话理由）
- 豁免：任务不涉及任何 `versions/` 产出（如纯 SOP / 脚本 / 知识库变更）时，小节只写一行「无版本关联产出，豁免」

**W32 卡点②变更摘要表**：卡点②向用户展示变更摘要时，必须用固定 7 列表格列示，与卡点①动作明细表逐行对应：

- 表头固定：`序号 | 动作 | 目标 | 修改说明 | 验证方式 | 验证过程 | 验证结果`
- 「验证过程」列写实际执行的命令或检查动作及命中位置（如 `grep -n "W32" <文件>` 命中第 N 行），禁止只写「已验证」
- 「验证结果」列枚举 `通过` / `不通过`，附实际输出要点（如 `命中 3 处`、`4/4`）

### §3.5 验收标准规则

**W18 评分维度表**：凡有「评分 ≥N 通过」的验收，必须定义：维度名 + 各维度分值 + 满分 + 通过线 + 分档处置（通过/返工/重写的分数区间）。维度名全项目唯一，禁止同一角色出现两套维度名。

**W19 通过线注册表**（唯一权威定义在 `docs/verification/quality-gates.md`，此处仅引用）：PRD ≥80 / 原型 ≥90 / 复原 ≥90（80-89 有条件通过）/ 操作文档 ≥85 / KB ≥90。

**W20 重试上限**：任何自动返工循环统一「最多 2 次」（即首次 + 2 次返工 = 3 次尝试后仍未通过则暂停并向用户报告）。全项目禁止出现其他重试次数。

**W21 机器可验标注**：检验清单每项标注【机器可验】（附 grep/脚本/命令）或【人工判定】（附判定要点）。机器可验项占比目标 ≥ 60%。

**W22 零编造**：SOP 中引用的事实（脚本存在性、参数、文件路径）必须与实际代码库一致；引用不存在的脚本/文件 = P0 缺陷。规划中的能力必须标注「（规划未实施）」并移出正式路由。

### §3.6 文档间一致性规则

**W23 双入口同步**：`AGENTS.md` 与 `CLAUDE.md` 中的路由表、卡点描述、阈值必须逐条一致；修改其一必须同步另一（引用 W11）。

**W24 registry 同步**：`config/project.yaml` 的 `agents.registry` 只登记实际会被调度的 agent；已停用 agent 文档必须删除文件并同步移除 registry 条目与入口路由引用。

**W25 版本数据同步**：`config/project.yaml` 的 `version.versions` 列表与 `STATE.md` 版本表由 `state_manager.py refresh` 保持一致；创建/归档版本的操作流程必须包含两处的同步步骤。

**W26 阈值/文件名全局唯一**：同一概念（评审报告文件名、通过线、重试次数、维度名）在任何两个文档中写法不一致 = P0 缺陷，验收时用 §4 的 grep 命令检查。

**W27 HTML 生成校验**：PRD/操作文档的 HTML 渲染版生成后、卡点②提交前，必须通过 `python3 scripts/prd_html_check.py <html>` 全部断言（6 类：标签配对 / CSS 变量完整性 / mermaid 图源 MD-HTML 一致 / 原型嵌入完整性 / 章节锚点连通 / 标注点内容一致），任一 FAIL 不得 commit。断言定义与防线背景见 `docs/agents/prd_stages/html_render.md` 检验清单。引用 W21 机器可验标注。

## §4 检验清单
