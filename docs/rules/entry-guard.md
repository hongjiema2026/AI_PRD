## §2 修改分档

### §2.1 允许修改（无需确认）

- 任务路由表新增行（新任务类型 → Skill + Pipeline/Agent）；新增后必须同步另一入口（引用规则 W23）
- 版本号更新（跟随 `config/project.yaml`）
- 修正错别字或格式

### §2.2 需用户明确指令才可修改

- 删除或重命名 §1 列出的任何章节
- 修改启动序列步骤
- 更改 SOP 流程定义（卡点①/② 的判定规则）
- 修改任务路由表列结构
- 移除路由表现有任务类型

### §2.3 禁止（除非用户明确要求且理解影响）

- 嵌入流水线逻辑或细节 → 应写入 `docs/pipelines/`
- 嵌入 Agent 指令 → 应写入 `docs/agents/`
- 嵌入检验规则 → 应写入 `docs/verification/`
- CLAUDE.md 总行数超过 160 行（定位为「项目工作手册目录」，超限优先外置而非削章节）
- 修改文件编码或添加非 Markdown 内容
- 路由表引用不存在的文件或未实施的能力（引用规则 W22；规划能力须标注「（规划未实施）」且不得进入正式路由表）

## §3 编辑前置条件

1. 先完整读取目标入口文件当前内容
2. 评估修改属于 §2 哪一档，按档位执行
3. 涉及路由表/卡点/阈值的修改，同一 commit 内同步另一入口（W23）
4. 不确定档位时，向用户确认而非自行决定

## §4 流程红线（强制，违反即流程事故）

### 4.1 Plan Mode 审批红线

- **绝对禁止**在 Plan Mode 下调用 `ExitPlanMode`（未等用户明确批准）
- **绝对禁止**在 Plan Mode 下编辑任何文件（计划文件除外）
- **绝对禁止**在 Plan Mode 下运行任何非只读工具
- 批准信号判定：见 `docs/rules/sop-writing-standard.md` W13（唯一权威定义）
- 用户说「走计划模式」时，必须先读取相关文件，制定完整计划，再请用户审批

### 4.2 校验流程红线

- **原型修改后必须执行**完整 Tester 验证流程：
  1. 浏览器预览验证所有功能路径
  2. 生成 `agent_comm/{task_id}/03_proto_test_report.md`
  3. 报告必须包含测试用例、结果、评分
  4. 评分 ≥90 分方可认为通过（通过线见 `docs/verification/quality-gates.md` §1）
- **PRD 修改后必须同步** MD + 主 HTML + 独立原型 HTML 三文件
- **禁止**在用户未确认的情况下直接报告「已完成」

### 4.3 Git 提交红线

- **禁止**在用户未明确说「提交」/「commit」（或批准的计划中包含提交步骤）时执行 `git commit`
- 提交前必须运行 `git status` 核对暂存范围；发现混入无关文件（如 `versions.zip`、日志、其他任务的脏改动）必须先剔除
- 提交信息必须描述「做了什么」和「为什么」

### 4.4 多步骤任务红线

- 涉及多文件修改时，按阶段/批次汇报（一个已批准计划内的一个阶段算一批），禁止无汇报连续推进多个未汇报批次
- 用户提出新需求时，必须先评估是否需要重新进入 Plan Mode

### 4.5 自纠机制

- 发现自己可能违反上述红线 → **立即停止**，向用户汇报违规情况
- 不隐瞒、不绕过、不事后补报
